# Разбор сценариев Ansible

## Введение

В этой работе я разобрал пять playbook, которые решают типовые задачи администрирования Ubuntu-серверов. Ansible описывает не последовательность ручных команд, а желаемое состояние системы. Поэтому большинство его модулей идемпотентны: при повторном запуске они не делают изменение, если сервер уже находится в нужном состоянии.

Имена после `name` нужны для читаемого вывода. `hosts` выбирает хост или группу из inventory, `become: true` включает повышение привилегий через `sudo`, а `tasks` содержит задачи, которые выполняются сверху вниз.

## 1. Установка и настройка Nginx

### Назначение всего playbook

Сценарий `01-nginx.yml` настраивает хосты из группы `NGINX`: обновляет индекс пакетов, устанавливает Nginx, запускает службу, включает ее автозапуск и создает собственную главную страницу.

`become: true` нужен потому, что обычный пользователь не может устанавливать системные пакеты, управлять службами и записывать файлы в `/var/www/html`. После повышения привилегий эти действия выполняются от имени `root`.

### Задача Update apt cache

Модуль `ansible.builtin.apt` управляет пакетами в Debian и Ubuntu.

- `update_cache: true` обновляет локальный список доступных пакетов. Это аналог `apt-get update`, но установленные программы на этом шаге еще не обновляются.
- `cache_valid_time: 3600` задает срок актуальности кэша в секундах. Если кэш обновлялся меньше часа назад, Ansible не будет обращаться к репозиториям еще раз.

После задачи на сервере будет актуальный индекс пакетов. Параметр `cache_valid_time` уменьшает количество лишних обращений к репозиториям и ускоряет повторные запуски.

### Задача Install Nginx

Модуль `apt` проверяет наличие пакета и при необходимости устанавливает его.

- `name: nginx` задает имя пакета.
- `state: present` означает, что пакет должен присутствовать. Это не обязательно последняя версия: главное, чтобы Nginx был установлен.

После выполнения пакет `nginx` и его зависимости будут установлены. Если пакет уже есть, задача завершится без переустановки.

### Задача Ensure Nginx is running and enabled

Модуль `ansible.builtin.service` управляет системной службой.

- `name: nginx` выбирает службу Nginx.
- `state: started` требует, чтобы служба была запущена сейчас. Остановленная служба будет запущена, уже работающая не будет перезапущена.
- `enabled: true` включает автоматический запуск при загрузке ОС.

После выполнения Nginx работает и автоматически запускается после перезагрузки сервера.

### Задача Create a custom index.html

Модуль `ansible.builtin.copy` создает файл и контролирует его содержимое и права.

- `content` содержит HTML, который будет записан в файл.
- `dest: /var/www/html/index.html` указывает путь назначения. Если файл существует, но отличается, он будет заменен.
- `owner: www-data` задает владельца файла.
- `group: www-data` задает группу файла.
- `mode: "0644"` дает владельцу право чтения и записи, а группе и остальным пользователям только чтение.

После задачи главная страница Nginx показывает строку `Hello! My name is Student Name` в заголовке первого уровня.

### Проверка Nginx

Состояние службы и страницы можно проверить командами:

```bash
systemctl is-active nginx
systemctl is-enabled nginx
curl http://localhost
```

Ожидается вывод `active`, `enabled` и содержимое созданного HTML-файла. С другого компьютера можно открыть `http://IP_СЕРВЕРА/`. Если соединения нет, дополнительно проверяются firewall, порт 80 и адрес сервера.

### Идемпотентность

Если Nginx уже установлен, `state: present` не переустановит его. Работающая служба не запустится второй раз, включенный автозапуск не изменится, а файл копируется заново только при отличии содержимого или атрибутов. Кэш APT не обновляется, если ему меньше часа. Поэтому второй запуск обычно возвращает `ok`, а не `changed`.

## 2. Создание пользователя newadmin

### Назначение всего playbook

Сценарий `02-create-user.yml` выполняется на `ubuntu_vm`. Он создает пользователя `newadmin`, назначает ему оболочку Bash и дополнительные группы, после чего командой `id` проверяет результат и выводит его в консоль Ansible.

Для создания учетной записи и изменения файлов `/etc/passwd`, `/etc/group` и `/etc/shadow` нужны права администратора, поэтому используется `become: true`.

### Задача Create new user with password

Модуль `ansible.builtin.user` управляет локальными пользователями.

- `name: newadmin` задает имя учетной записи.
- `groups: root,sudo` перечисляет дополнительные группы. Группа `sudo` дает возможность выполнять разрешенные административные команды через `sudo`. Группа `root` может давать доступ к файлам с соответствующей группой, но не делает пользователя суперпользователем.
- `append: true` добавляет указанные группы к уже имеющимся. Без `append` не перечисленные дополнительные группы могли бы быть удалены.
- `password: "{{ '123' | password_hash('sha512') }}"` вычисляет SHA-512-совместимый хеш пароля и передает его модулю.
- `shell: /bin/bash` назначает Bash оболочкой входа.
- `state: present` требует существования пользователя. Если он уже существует, Ansible проверяет и корректирует его параметры.

После выполнения в системе существует `newadmin`, у него есть оболочка `/bin/bash`, пароль и членство в группах `root` и `sudo`. Пароль `123` очень слабый и допустим только в учебном примере.

### Почему передается хеш

Linux не хранит открытые пароли в `/etc/shadow`. Там записывается результат одностороннего хеширования с солью. При входе система хеширует введенный пароль и сравнивает результат с сохраненным значением. Поэтому модулю `user` на Linux передается хеш, а не обычная строка пароля.

Однако исходный пароль все равно виден внутри playbook. В настоящем проекте хеш или исходный секрет следует хранить в Ansible Vault. Кроме того, случайная соль фильтра `password_hash` может дать новый хеш при следующем запуске. Для стабильной идемпотентности лучше заранее создать один хеш и хранить его в зашифрованной переменной.

### Задача Verify user creation

Модуль `ansible.builtin.command` запускает программу на удаленном сервере без обработки строки командной оболочкой.

- `id newadmin` выводит UID, основной GID и список групп пользователя.
- `register: user_info` сохраняет весь результат задачи в переменную `user_info`. Стандартный вывод находится в `user_info.stdout`, ошибки в `user_info.stderr`, код возврата в `user_info.rc`.
- `changed_when: false` добавлен в рабочий файл, потому что команда `id` только читает данные и ничего не меняет. В исходном задании этой строки не было, поэтому Ansible мог неточно показывать задачу как изменившую сервер.

Если пользователь отсутствует, команда возвращает ошибку и playbook останавливается. Если пользователь существует, сервер не изменяется.

### Задача Display user information

Модуль `ansible.builtin.debug` выводит данные во время запуска playbook.

- `msg` задает текст сообщения.
- `{{ user_info.stdout }}` подставляет вывод команды `id newadmin`.

На сервере задача ничего не меняет. В консоли появляется UID, GID и группы созданного пользователя.

### Проверка пользователя

```bash
id newadmin
getent passwd newadmin
groups newadmin
sudo passwd -S newadmin
```

`id` и `groups` показывают идентификаторы и группы, `getent passwd` подтверждает наличие учетной записи и оболочки, а `passwd -S` показывает состояние пароля.

### Подключение по SSH

Для парольного входа используется команда:

```bash
ssh newadmin@IP_СЕРВЕРА
```

Это сработает, если установлен и запущен SSH-сервер, порт доступен, а в `sshd_config` разрешена парольная аутентификация. Более безопасный способ — добавить публичный ключ в `/home/newadmin/.ssh/authorized_keys` модулем `ansible.posix.authorized_key`. Данный playbook ключ не устанавливает.

### Разница между root и sudo

`root` — учетная запись с UID 0 и постоянными неограниченными правами. Пользователь группы `sudo` остается обычным пользователем и получает повышенные права только при выполнении команды через `sudo`. Такие действия можно ограничивать политикой и фиксировать в журнале. Членство в группе `root` само по себе не присваивает UID 0 и не заменяет группу `sudo`.

## 3. Обновление всех пакетов

### Назначение всего playbook

Сценарий `03-update-packages.yml` работает на `ubuntu_vm`, обновляет индекс APT и все пакеты, удаляет ненужные зависимости, очищает устаревший кэш, проверяет необходимость перезагрузки и при необходимости перезагружает сервер.

`become: true` нужен для операций APT и перезагрузки. `gather_facts: true` включает сбор фактов о системе до запуска задач. В частности, используется факт `ansible_facts['os_family']`.

### Задача Update apt cache

- `update_cache: true` обновляет индекс репозиториев.
- `cache_valid_time: 3600` пропускает обновление, если кэш моложе часа.
- `register: apt_update` сохраняет результат задачи.
- `when: ansible_facts['os_family'] == "Debian"` запускает ее только на Debian-подобной ОС.

После выполнения APT знает об актуальных версиях пакетов.

### Задача Upgrade all packages

- `upgrade: dist` соответствует `apt-get dist-upgrade`. Он обновляет систему и при необходимости может устанавливать новые либо удалять конфликтующие зависимости.
- `autoremove: true` удаляет автоматически установленные зависимости, которые больше не требуются.
- `autoclean: true` удаляет из кэша старые пакеты, которые больше нельзя скачать из репозиториев.
- `register: apt_upgrade` сохраняет отчет задачи.
- `when` ограничивает выполнение семейством Debian.

После задачи установленные пакеты обновлены, ненужные зависимости удалены, а часть кэша освобождена. Если убрать `autoremove`, старые зависимости останутся. Если убрать `autoclean`, обновление пройдет, но устаревшие файлы пакетов продолжат занимать место.

### Задача Check if reboot is required

Модуль `ansible.builtin.stat` получает сведения о файле и не изменяет его.

- `path: /var/run/reboot-required` задает проверяемый файл. Ubuntu создает его, когда после обновления ядра или важных библиотек требуется перезагрузка.
- `register: reboot_required_file` сохраняет результат. Признак наличия находится в `reboot_required_file.stat.exists`.
- `when` выполняет проверку только на Debian-подобных системах.

### Задача Reboot server if required

Модуль `ansible.builtin.reboot` инициирует перезагрузку, ждет отключения хоста, его повторного появления и успешного выполнения тестовой команды.

- `msg` содержит причину перезагрузки.
- `connect_timeout: 5` ограничивает время отдельной попытки подключения пятью секундами.
- `reboot_timeout: 300` дает серверу до 300 секунд на перезагрузку и подтверждение готовности.
- `pre_reboot_delay: 0` не добавляет задержку перед перезагрузкой.
- `post_reboot_delay: 30` ждет 30 секунд после возврата сервера, чтобы основные службы успели запуститься.
- `test_command: whoami` проверяет, что на сервере уже можно выполнять команды.
- `when` запускает перезагрузку только при наличии файла `reboot-required`.

Модуль определяет факт перезагрузки по изменению идентификатора загрузки, ожидает восстановления подключения и выполняет `test_command`. Успешный код возврата означает, что сервер готов продолжать playbook.

В рабочем файле я добавил проверку семейства ОС и фильтр `default(false)`. В исходном варианте на не-Debian-системе задача `stat` была бы пропущена, после чего обращение к отсутствующему полю `.stat.exists` могло завершить playbook ошибкой.

### Задача Display update status

Модуль `debug` выводит список сообщений.

- `apt_update is changed` показывает, обновлялся ли кэш фактически.
- `apt_upgrade is changed` показывает, внесла ли задача обновления изменения.
- `reboot_required_file.stat.exists` показывает, требовалась ли перезагрузка.

Последнее значение правильнее называть `Reboot required`, а не `Reboot performed`: наличие файла говорит о необходимости перезагрузки до задачи, но само по себе не является отдельным доказательством ее успешного завершения.

### Почему проверяется семейство ОС

Ubuntu и Debian используют APT, RHEL-подобные системы — DNF, а другие системы могут использовать свои менеджеры пакетов. Проверка не позволяет запустить Debian-модуль на неподходящей ОС и получить ошибку. Она также делает назначение playbook явным.

## 4. Резервное копирование конфигурации

### Назначение всего playbook

Сценарий `04-backup-configs.yml` создает на `ubuntu_vm` каталог резервной копии с текущей датой и копирует туда конфигурацию SSH, Nginx и файл hosts. `become: true` позволяет читать системные файлы и создавать копии с повышенными правами.

### Переменные

- `backup_dir` задает путь `/home/user/backups/ДАТА`.
- `{{ ansible_date_time.date }}` берется из фактов Ansible и обычно выглядит как `2026-09-30`.
- `files_to_backup` содержит три абсолютных пути исходных файлов.

Дата разделяет копии по дням. При повторном запуске в тот же день используется тот же каталог, поэтому это дневная копия, а не отдельный архив каждого запуска.

### Задача Create backup directory

Модуль `ansible.builtin.file` управляет объектом файловой системы.

- `path: "{{ backup_dir }}"` задает вычисленный каталог.
- `state: directory` требует, чтобы путь существовал именно как каталог. Отсутствующий каталог будет создан.
- `mode: "0755"` дает владельцу чтение, запись и вход, остальным — чтение и вход.

После задачи каталог существует. Так как явно не заданы `owner` и `group`, при создании через `become` он обычно будет принадлежать `root`.

### Задача Copy each configuration file

Модуль `ansible.builtin.copy` выполняется в цикле.

- `src: "{{ item }}"` берет очередной путь из списка.
- `dest: "{{ backup_dir }}/"` указывает каталог назначения. Исходное имя файла сохраняется.
- `remote_src: true` сообщает, что исходник находится на управляемом сервере. Без него Ansible искал бы файл на управляющем компьютере.
- `loop: "{{ files_to_backup }}"` повторяет задачу для каждого элемента списка.
- `ignore_errors: true` продолжает playbook, даже если отдельный файл скопировать не удалось.

В каталоге должны появиться `sshd_config`, `nginx.conf` и `hosts`.

### Риск ignore_errors

Игнорирование ошибки полезно, если некоторые компоненты намеренно могут отсутствовать. Но для резервного копирования оно опасно: playbook продолжится при отсутствии файла, нехватке прав, заполненном диске или ошибке чтения. В результате администратор может принять неполную копию за успешную.

### Проверка копирования

Без просмотра журнала можно проверить каталог:

```bash
ls -l /home/user/backups/$(date +%F)
test -f /home/user/backups/$(date +%F)/sshd_config
test -f /home/user/backups/$(date +%F)/nginx.conf
test -f /home/user/backups/$(date +%F)/hosts
```

В самом playbook лучше выполнить `stat` для каждой ожидаемой копии и затем `assert`, проверяющий `item.stat.exists`. Более надежная проверка дополнительно сравнивает контрольные суммы оригиналов и копий.

## 5. Установка Docker и создание контейнеров

### Назначение и исправление структуры

Исходный фрагмент начинался со строки `hosts: ubuntu_vm` без дефиса и названия play. Такой YAML не является корректным списком play Ansible. В `05-docker-containers.yml` начало исправлено на `- name`, после которого идут `hosts`, `become`, `vars` и `tasks`.

Сценарий подключает официальный репозиторий Docker, устанавливает Docker Engine и зависимости, загружает образ Ubuntu и создает четыре контейнера на хостах `ubuntu_vm`.

### Переменные

- `container_count: 4` — количество контейнеров.
- `default_container_name: docker` — основа имени.
- `default_container_image: ubuntu` — используемый образ. Без тега подразумевается `latest`.
- `default_container_command: sleep 1d` — команда внутри контейнера, ожидающая одни сутки.

### Задача Install aptitude

- `name: aptitude` выбирает пакет.
- `state: latest` устанавливает его либо обновляет до последней доступной версии.
- `update_cache: true` сначала обновляет индекс APT.

`aptitude` исторически использовался Ansible для некоторых операций обновления. Современный модуль `apt` во многих случаях работает и без него, но в учебном сценарии он устанавливается заранее.

### Задача Install required system packages

Параметр `pkg` принимает список пакетов, `state: latest` требует их последние версии, а `update_cache: true` обновляет индекс.

- `apt-transport-https` нужен старым версиям APT для HTTPS-репозиториев; в современных Ubuntu поддержка обычно встроена.
- `ca-certificates` содержит доверенные корневые сертификаты для проверки HTTPS.
- `curl` загружает данные по HTTP/HTTPS и используется для диагностики.
- `software-properties-common` содержит средства управления репозиториями.
- `python3-pip` устанавливает пакеты Python.
- `virtualenv` создает отдельные Python-окружения.
- `python3-setuptools` предоставляет инструменты сборки и установки Python-пакетов.

После задачи система подготовлена для работы с внешним репозиторием и Python-зависимостями.

### Задача Add Docker GPG apt key

Модуль `ansible.builtin.apt_key` добавляет ключ доверия APT.

- `url` указывает официальный публичный ключ Docker.
- `state: present` гарантирует его наличие.

Ключ позволяет проверить, что пакеты подписаны Docker и не были изменены. На современных системах `apt_key` считается устаревающим подходом; предпочтительнее отдельный keyring и параметр `signed-by`.

### Задача Add Docker repository

Модуль `ansible.builtin.apt_repository` управляет источником пакетов.

- `repo` содержит тип `deb`, URL, кодовое имя Ubuntu `jammy` и канал `stable`.
- `state: present` гарантирует наличие репозитория.

`jammy` соответствует Ubuntu 22.04. На другой версии ОС значение следует получать из `ansible_distribution_release`, иначе репозиторий может оказаться несовместимым.

### Задача Update apt and install docker-ce

- `name: docker-ce` задает Docker Community Edition.
- `state: latest` устанавливает либо обновляет его.
- `update_cache: true` обновляет индекс после подключения репозитория.

После задачи Docker Engine установлен. В рабочий файл дополнительно включена задача `service`, которая гарантирует состояние `started` и `enabled`, так как одной установки пакета недостаточно для явной гарантии запуска во всех окружениях.

### Задача Install Docker module for Python

- `name: python3-docker` — Docker SDK для Python.
- `state: present` гарантирует его наличие.

В старых версиях коллекции через этот SDK работали `docker_container`, `docker_image`, `docker_network`, `docker_volume` и другие модули. В новых версиях `community.docker` часть модулей общается с Docker API через встроенный код и библиотеку `requests`, поэтому точная необходимость `python3-docker` зависит от версии коллекции. В учебном сценарии пакет обеспечивает совместимость с распространенными версиями Ansible.

### Задача Pull default Docker image

Модуль `community.docker.docker_image` управляет образами.

- `name` получает значение `ubuntu` из переменной.
- `source: pull` требует загрузить образ из реестра.

После задачи образ Ubuntu доступен локальному Docker daemon.

### Задача Create default containers

Модуль `community.docker.docker_container` управляет контейнерами.

- `name: "{{ default_container_name }}{{ item }}"` соединяет слово `docker` с текущим номером.
- `image` выбирает образ Ubuntu.
- `command` задает `sleep 1d`.
- `state: present` гарантирует существование контейнера, но не требует, чтобы он работал.
- `with_sequence: "count={{ container_count }}"` создает последовательность от 1 до 4.

Имена контейнеров: `docker1`, `docker2`, `docker3`, `docker4`. Проверить их можно командой:

```bash
docker ps -a
```

Если убрать `state: present`, в актуальных версиях `community.docker.docker_container` применяется значение по умолчанию `started`. Тогда контейнеры будут не только созданы, но и запущены. После завершения `sleep 1d` примерно через сутки они остановятся, потому что политика автоматического перезапуска не задана.

### Почему устанавливаются зависимости до Docker

До установки Docker системе нужны доверенные сертификаты и возможность получить пакеты через HTTPS. Средства управления репозиториями добавляют новый источник APT, а Python-компоненты обеспечивают выполнение Docker-модулей Ansible. Такой порядок позволяет сначала подготовить доверенный источник, затем установить сам Docker и только после этого обращаться к его API.

### Итог и идемпотентность

После успешного запуска установлен и запущен Docker, загружен образ Ubuntu и существуют четыре контейнера. Повторный запуск не дублирует ключ, репозиторий, образ или контейнеры. Пакеты со `state: latest` могут обновиться, если в репозитории появились новые версии. Контейнер пересоздается только тогда, когда его фактическая конфигурация не соответствует описанной и изменение нельзя применить на месте.

## Общий вывод

Эти сценарии показывают основные принципы Ansible: выбор группы хостов, повышение привилегий, использование переменных, циклов, условий и зарегистрированных результатов. Самое важное преимущество по сравнению с набором shell-команд — контроль требуемого состояния. При повторном запуске Ansible обычно меняет только то, что действительно отличается от playbook.

При переносе примеров в рабочую инфраструктуру я бы дополнительно вынес пароли в Ansible Vault, использовал SSH-ключи, отказался от `ignore_errors` без последующей проверки, заменил устаревающий `apt_key`, определял версию Ubuntu автоматически и добавил проверки доступности сервисов после настройки.
